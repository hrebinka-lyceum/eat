# Облік шкільного харчування — фронтенд

Веборієнтована система обліку харчування в навчальному закладі: меню на день,
замовлення учнів, облік порцій для їдальні, звітність для бухгалтерії.
Інтерфейс українською, часовий пояс `Europe/Kyiv`.

Бекенд — Supabase (PostgreSQL + RLS + Edge Functions), розгорнутий окремо.
Цей репозиторій містить **лише фронтенд**.

## Стек

| Призначення | Інструмент |
|---|---|
| Збірка, dev-сервер | Vite, TypeScript |
| UI | React, Tailwind CSS v4, shadcn/ui (Radix), lucide-react |
| Дані | `@supabase/supabase-js`, `@tanstack/react-query` |
| Маршрутизація | `react-router-dom` |
| Графіки | `recharts` |
| Дати | `date-fns` (локаль `uk`) |
| Тема | `next-themes` (світла за замовчуванням, вибір зберігається) |
| Тести | Vitest, React Testing Library, jsdom |
| Лінт | oxlint |

## Запуск

```bash
npm install
cp .env.example .env   # і вписати справжні значення
npm run dev            # http://localhost:5173/eat/
```

Застосунок публікується на GitHub Pages у підкаталозі, тому `base` у
`vite.config.ts` — `/eat/`, а роутер бере `basename` із
`import.meta.env.BASE_URL`. Звідси префікс `/eat/` і в локальній адресі.

### Скрипти

| Команда | Що робить |
|---|---|
| `npm run dev` | dev-сервер |
| `npm run build` | `tsc -b` + збірка в `dist/` + копія `index.html` → `404.html` |
| `npm test` | Vitest, один прогін |
| `npm run test:watch` | Vitest у режимі спостереження |
| `npm run test:coverage` | звіт про покриття |
| `npm run preview` | локальний перегляд зібраного `dist/` |
| `npm run lint` | oxlint |
| `npm run gen:types` | генерація `src/types/database.ts` зі схеми (потребує `SUPABASE_ACCESS_TOKEN`) |

Копія `index.html` у `404.html` обов'язкова: без неї прямі посилання на
статичному хостингу дають 404 замість сторінки застосунку.

## Змінні оточення

| Змінна | Де брати |
|---|---|
| `VITE_SUPABASE_URL` | Supabase → Project Settings → API |
| `VITE_SUPABASE_ANON_KEY` | там само, **anon / publishable** |

У фронтенді живе виключно публічний ключ. `service_role` сюди не потрапляє
ніколи: доступ до рядків вирішує RLS на сервері. У CI ті самі змінні
беруться із секретів репозиторію.

## Структура

```
src/
  api/         єдиний шар звернень до Supabase, згрупований за сутностями
  auth/        сесія, профіль, охорона маршрутів, перевірка прав
  components/
    ui/        shadcn
    common/    діалоги, стани завантаження, експорт, каркас звітів
    charts/    обгортки recharts
    layout/    каркаси для співробітників і для учня
  hooks/       дані, спільні для кількох екранів
  lib/         supabase-клієнт, формати, дати, CSV, людські помилки, ключі кешу
  pages/       екрани, згруповані за ролями
  types/       типи бази даних
tests/
  lib/         чиста логіка
  api/         контракти запитів до бази
  ui/          компонентні тести екранів
```

## Архітектурні правила

- **Компоненти не викликають `supabase.from(...)` напряму** — лише через `src/api/`.
  Це єдина межа, через яку проходять усі дані.
- **Права забезпечує RLS**, а не інтерфейс. Приховані пункти меню — зручність;
  будь-яка спроба недоступної дії завершується помилкою сервера, і це нормальний
  результат.
- **Поля вартості не запитуються там, де їх не має бути.** Для частини ролей
  сервер фільтрує суми сам, але не всі цінові колонки захищені політиками, тому
  для таких екранів існують окремі запити без цін.
- **Рішення про час приймає сервер.** Дедлайн прийому замовлень не обчислюється
  на клієнті: годинник браузера не є джерелом істини.
- **Ключі кешу react-query** централізовані в `lib/queryKeys.ts`.
- У хуках використовується `isLoading`, а не `isPending`: вимкнений запит
  назавжди лишається `pending`.

## Ролі

У системі п'ять ролей; маршрути закриті охороною за роллю, домівка в кожної своя.
Дві з них (класний керівник і учень) не бачать жодних сум — ані в інтерфейсі,
ані у відповідях сервера.

## Тести

```bash
npm test
```

Тести виконуються в `TZ=UTC` — так само, як у CI, щоб часовий пояс розробника
не ховав помилок роботи з датами. `tests/` — окремий проєкт TypeScript
(`tsconfig.test.json`), тож `npx tsc -b` перевіряє і їх. У CI тести проходять
перед збіркою: зламаний тест зупиняє публікацію.

## Публікація

GitHub Actions на push у `main`: встановлення залежностей → тести → збірка →
перевірка наявності `404.html` → деплой на GitHub Pages. У налаштуваннях
репозиторію Pages мають працювати через GitHub Actions.
